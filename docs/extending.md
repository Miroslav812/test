# Добавление автотестов

1. Добавьте endpoint-клиент в `src/restkit/apis/`. Клиент возвращает `httpx.Response`,
   а assertions остаются в тестах: это позволяет тестировать отрицательные сценарии.
2. Добавьте модели ответов в `contracts.py`. Используйте строгие типы и ограничения,
   соответствующие реальному OpenAPI. Изменения API должны приводить к понятному падению.
3. Создавайте данные через фабрики с уникальным идентификатором; не полагайтесь на
   заранее существующий ID или порядок выполнения тестов.
4. Регистрируйте созданные ресурсы в fixture до проверок контракта. В teardown удаляйте
   их, обрабатывая уже удалённые записи. Ошибка cleanup должна быть видна в отчёте.
5. Отметьте каждый изменяющий данные тест `@pytest.mark.mutation`. Эта метка управляет
   пропуском записей во внешнем режиме; pytest запускает только явно разрешённые mutations.
6. Добавьте smoke/contract/negative-метки по назначению. В Allure передавайте описание
   действия, а не реальные credentials или персональные данные.
7. Проверяйте статус, контракт и наблюдаемый результат: сохранение, отсутствие изменений
   после отклонённого запроса, удаление, фильтрацию. Только статус 200 недостаточен.
8. Выполните `make check`, `make test` и `make parallel`.

Новые зависимости добавляются через `uv add` (инструменты — `uv add --dev`). Вместе
коммитьте `pyproject.toml` и `uv.lock`. CI устанавливает только зафиксированный lockfile.

Не добавляйте retries для POST/PATCH/DELETE без гарантированной идемпотентности API.
Не отключайте TLS для исправления проблем сертификатов — настройте доверенный CA.
Оставляйте токены в environment/Secrets, а не в коде, pytest-параметрах или отчётах.

## UI

Selenium-сценарии описаны в [ui-testing.md](ui-testing.md). Добавляйте взаимодействие
и локаторы в Page Objects, а проверки поведения — в `tests/ui/`. Комментируйте причины
неочевидных решений (например, ожидание перерисовки или ограничения очистки данных),
а не повторяйте в комментариях очевидное действие строки кода. После изменения UI
проверяйте `make ui` и объединённый набор `make all`; API отдельно — `make test`.

Для гонок и восстановления используйте [advanced-testing.md](advanced-testing.md).
Регистрируйте email через `owned_payloads` до прямого API/UI создания: очистка должна
работать и тогда, когда неизвестен ID успешного запроса. `parallel_requests` запускает
до восьми готовых клиентов через барьер с таймаутом и сохраняет порядок ответов.
Не задавайте случайный порядок победителей PATCH, если API не обещает версионирование.
