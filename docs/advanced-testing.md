# Проверки согласованности, конфликтов и восстановления

Набор `advanced` содержит 43 API и 26 UI проверок. Всего в проекте: 120 тестов.
Приложение запускается локально с отдельным хранилищем на worker; сценарии не требуют
внешнего стенда и автоматически пропускаются в `--api-mode external`.

## API

`tests/api/test_consistency.py` проверяет:

- Имена на границах длины 1/100, Unicode, пробелы, обе роли и UTC-даты.
- Попытки изменить id/email/role/created_at или передать лишнее поле через PATCH.
  Отклонение проверяется по полному снимку записей: валидная часть запроса тоже не сохраняется.
- Невалидные PATCH и JSON-тела без побочных изменений.
- Пагинацию с размером страницы 1/2/3/100 до и после удаления средней записи и добавления новой.
  Проверяются порядок, total, полнота, отсутствие дубликатов и пустая страница после конца списка.
- Повторное использование email удалённого пользователя с новым ID.
- Отклонение PATCH удалённой записи без её восстановления.
- Авторизацию POST/GET/PATCH/DELETE и отсутствие побочных изменений после 401.
- Отказ на неподдерживаемый PUT без изменения данных.

Четыре синхронизированных сценария запускают восемь HTTP-клиентов:

| Операция | Проверяемый результат |
| --- | --- |
| Создание с одним email | Один 201 и семь 409; сохранена ровно одна запись |
| Создание разных пользователей | Все 201; уникальные ID, каждый ответ соответствует запросу, все записи сохранены |
| Удаление одной записи | Один 204 и семь 404; записи больше нет |
| Обновление одного имени | Все 200 подтверждают имя своего запроса; итоговое имя принадлежит одному из запросов, остальные поля неизменны |

У PATCH нет версии/ETag, поэтому тест не требует конкретного последнего победителя и
не заявляет защиту от потерянных обновлений. Это тесты корректности, а не нагрузочный
профиль: нет требований к RPS/latency, адаптивной нагрузки или случайных порогов времени.

## UI

`tests/ui/test_advanced_flows.py` проверяет:

1. Неверный email не создаёт запись; исправление формы позволяет создать пользователя.
2. Имя из пробелов проходит HTML required, отклоняется сервером, а затем исправляется в том же редакторе.
3. Отмена редактирования не изменяет UI/API-данные, в том числе после refresh.
4. Удаление другим API-клиентом во время редактирования приводит к 404 и не восстанавливает запись.
5. Два браузера видят изменения после refresh; выход первого не мешает второму удалить запись.
6. Потеря сети браузера не создаёт запись; после восстановления повторная попытка создаёт ровно одну.
7. Список из 102 пользователей пересекает границу API-страницы; последняя запись доступна для поиска и удаления.
8. Unicode и HTML в имени остаются текстом, а поиск корректно работает с регистром и кавычками.
9. После ошибки duplicate email удачная попытка очищает сообщение и сохраняет только допустимые записи.
10. Повторный вход сбрасывает старый фильтр, сохраняя сами API-данные.

Ещё 16 проверок в `test_form_behaviour.py` и `test_editor_states.py` покрывают:

- Обязательные поля имени/email: отклонение не очищает остальные значения,
  исправление создаёт ровно одну запись.
- Длину имени в формах создания и изменения: браузер ограничивает ввод до 100 символов,
  API сохраняет именно введённое значение.
- Сброс полей и роли после создания администратора; следующий пользователь получает роль user.
- Вход, создание и сохранение изменения клавишей Enter.
- Пустое имя в редакторе: нативная валидация сохраняет открытый редактор и позволяет исправление.
- Переключение между двумя пользователями: старый черновик не попадает в новую запись.
- Изменение имени под активным фильтром: строка исчезает из результата, а запись сохраняется.
- Внешние изменения и создание: обновление списка сохраняет фильтр и показывает свежие данные.
- Удаление редактируемой записи: форма закрывается, соседний пользователь не изменяется.
- Удаление устаревшей строки: 404 не мешает обновлению и следующей успешной операции.
- Выход и перезагрузку с открытыми формами: черновики, фильтр и ошибки сбрасываются,
  сохранённые записи остаются. Это два отдельных случая.
- Ошибку сети при PATCH: введённое имя остаётся в редакторе, повторное сохранение после
  восстановления меняет только имя существующего пользователя.
- Общий email в черновиках двух браузеров: один сохраняет запись, второй получает 409,
  сохраняет свой ввод и может исправить email без изменения первого пользователя.

Потеря сети задаётся через Chrome DevTools Protocol только внутри текущего браузера;
Chrome и Edge поддерживают этот сценарий. API-клиент наблюдения остаётся подключённым.
`finally` восстанавливает сеть и при падении теста. Selenium-клики и изменяющие API-запросы
не повторяются автоматически; повторная попытка — явный шаг пользовательского сценария.

`UserDraft` делает значения формы явными: `user_data.name`, `user_data.email`,
`user_data.role`. `read_user` объединяет повторяющееся чтение через API с проверкой
статуса и строгой схемы; assertions о поведении остаются в сценариях. Комментарии
на русском объясняют технические ограничения, шаги Allure — действия пользователя.

## Данные, ресурсы и отчёт

`owned_payloads` регистрирует уникальный email до отправки запросов. После теста
записи этого владельца собираются по всем страницам и удаляются. Общего reset хранилища
нет, поэтому cleanup не удаляет чужие записи. Снимки через `read_all_users` снимаются
после завершения конкурентных операций, а не во время изменения списка.

`browser_factory` регистрирует каждый WebDriver до настройки таймаутов и закрывает
все созданные сессии даже при ошибке закрытия одной из них. При падении сохраняются
screenshots и DOM обоих браузеров. Allure steps выделяют этап, на котором нарушился
контракт: создание, синхронизация, изменение, отказ или восстановление.

Команды из папки с `pyproject.toml`:

```powershell
uv run --frozen --no-default-groups --group ui pytest tests -m advanced --browser edge --headed
uv run --frozen --no-default-groups --group test pytest -m concurrency
uv run --frozen --no-default-groups --group ui pytest tests/ui -m resilience --browser edge
uv run --frozen --no-default-groups --group ui pytest tests --browser edge -n 2
```

Для Linux-контейнера браузер/драйвер задаются через `UI_BROWSER_BINARY`/`UI_DRIVER_PATH`,
а `--browser-no-sandbox` применяется только при ограничениях уже изолированного контейнера.
